# 应用内更新与 GitHub 发布

适用源码：0.8.0 / build 21，2026-10-16。更新组件为固定的 Sparkle 2.10.0；官方归档的 SHA-256、公钥和发行清单地址见 `Resources/Updates.json`。

## 用户会看到什么

- 独立版默认每天联网检查新版本；菜单“知会 → 检查更新…”和“设置 → 软件更新”可手动检查，设置中的“自动检查新版本”可关闭并保存偏好。
- 发现新版后使用 Sparkle 原生窗口确认下载、安装和重启。不会静默重启正在使用的应用。
- 录音启动、录音中、停止保存、模型下载、音频导入、切换会议及当前会议任务期间暂缓检查。若下载后才开始录音或任务，安装延后；完成后在设置中点击“安装更新并重启”。
- 安装请求通过正常退出事件进入现有 `AppDelegate`：保存笔记、保留音频队列、关闭本应用拥有的后台。保存失败时继续运行，不允许安装器提前替换仍在运行的应用。
- 更新替换 App，会议、录音、模型和缓存仍在应用外的用户资料目录。更新器不处理或上传会议内容，不重置系统权限；新旧签名不兼容时，macOS 仍可能重新要求声音权限。
- 源码开发包关闭发行更新，避免发行包覆盖开发环境；独立版才启动更新器。

公开的 **0.5.0 / build 16 没有更新器**，无法隔空获得这个功能。旧用户需要先手动安装一次包含更新器的版本，后续才能在应用内升级。只推送 Git 提交或打标签不会分发更新。

## 信任与密钥

正式清单地址：<https://github.com/zhutyler21/zhihui/releases/latest/download/appcast.xml>。每个正式 Release 的 `appcast.xml` 通过版本标签指向同一 Release 中的 ZIP。

版本清单和完整 ZIP 使用 Ed25519 签名。App 内嵌 `SUPublicEDKey`，启用 `SURequireSignedFeed` 与 `SUVerifyUpdateBeforeExtraction`。发布工具检查私钥和包内公钥是否一致，并验证生成后的签名；错误密钥不生成发行附件。框架下载固定版本和 SHA-256，签名前保留原生权限与符号链接，按辅助服务、辅助程序、框架、外层 App 的顺序签名。App 包内保留 Sparkle MIT 许可。

本次已生成此项目专用签名种子，存放于不提交的 `work/update-signing/ed25519.private-key`，目录权限 700、文件权限 600。**维护者必须将原私钥安全备份到仓库以外的保密位置，不能上传为 Release 附件，不能提交 Git，不能丢失或随意重新生成。** 公钥可以公开。后续机器使用安全恢复的原私钥，通过 `--key-file` 指定路径；无需使用钥匙串或导出 macOS 签名证书。

`xcrun swift scripts/setup-update-key.swift` 只用于尚未配置公钥的新项目，检测到已有公钥或私钥会拒绝覆盖。本仓库已配置公钥，不要为日常构建重新生成。未来更换私钥应按 Sparkle 官方密钥轮换规则单独处理。

Ed25519 更新签名与 macOS 代码签名不同，不代表 Developer ID 或 Apple 公证。公开发行仍应明确实际签名身份、公证状态和设备验证范围；需要平滑沿用声音权限时，保持应用标识和兼容的签名身份。当前本机包使用已配置的 Apple Development 身份，未公证，不作为跨机器授权保持的证明。

## 维护者发布流程

1. 更新 `scripts/build-app.sh` 的显示版本与递增 build，同时更新 `scripts/install-app.py` 的允许安装版本；build 必须高于已发布版本。DMG 和更新 ZIP 文件名从实际 App 读取，不再固定在 0.5.0。
2. 构建并验证完整独立版，保留发布所用代码签名身份：

   ```sh
   bash scripts/test-app-update.sh
   bash scripts/build-standalone.sh
   python3 scripts/build-dmg.py
   .venv/bin/python scripts/build-update.py --output dist/update-v0.8.0
   ```

   构建会联网取得固定 Sparkle 组件；不会下载或更换会议模型。`build-update.py` 只接受项目内 `dist/` 或 `work/` 中的独立版，核对运行依赖、签名、更新配置和私钥匹配，打包前后检查源 App 未改变。输出目录必须不存在，避免覆盖既有发行物。重新构建同版时先妥善保留旧产物，再选择新的输出目录。

3. 核对输出：`Zhihui-v0.8.0-macOS-arm64.zip`、已签名的 `appcast.xml`、`SHA256SUMS.txt`、本地验证用 `update-receipt.json`。不要编辑签名后的 XML；修改后必须重新签名。DMG 是首次安装入口，ZIP 是 Sparkle 使用的更新包，两者必须来自同一个最终 App。
4. 完成发布授权和源码脱敏检查后，将 DMG、更新 ZIP、`appcast.xml`、校验清单、对应源码及 FFmpeg/MLX 源码上传到同一个**非草稿、非预发布的正式 Release**，标签与清单中的版本一致，并将其设为 Latest。合并 DMG 和更新附件的校验值时，保留原文件名，不把私钥或本地验收资料混入附件。
5. 从 GitHub 下载清单和 ZIP，检查 HTTPS、签名与附件一致，再用真正的旧版验证更新。GitHub 无法连接时，手动检查会提示失败并可重试或打开下载页；后台检查失败不会影响本地会议。

`SUFeedURL` 使用 GitHub Latest 重定向，依赖正式 Release；不要把测试版本设为 Latest，也不要删除仍在发行清单中引用的附件。跨版本 build、系统最低要求和架构选择由 Sparkle 从实际包和清单判断。

## 接入阶段验证与边界

实际命令、日志、截图和签名产物位于不提交的 `work/auto-update-20261016/`。失败过的初次构建日志保留，后续成功记录不覆盖失败范围。

- `bash scripts/test-app-update.sh`：实际更新控制器的忙碌拒绝、下载/录音先后变化、延后安装、重复安装保护、失败后清理旧安装闭包、无新版、网络错误和开发包禁用。
- `.venv/bin/python -m unittest discover -s tests -p test_update_packaging.py -v`：6 项发布边界检查通过，拒绝开发包、QA 资料配置、未签名清单策略、错误清单地址、错误私钥，并保留既有输出。
- `bash scripts/test-native-state.sh`：改动前基线通过；应用状态、录音队列、延迟请求、切换和取消使用合成资料验证。
- `bash scripts/test-preflight-shutdown.sh`：实际 AppModel 在后台未初始化及启动失败时退出，保存音频队列。
- `bash scripts/test-markdown.sh`：实际 Markdown 保存、拒绝保存后保留草稿及会议切换保护。
- `scripts/install-app.py --self-test`：安装备份、回滚、模型副本校验及合成数据库不变。
- 完整独立包构建和签名审计：0.8.0 / build 21，89 个原生组件，实际最低系统 macOS 14.0；Sparkle 嵌套签名与相对依赖检查通过。
- 签名发布工具实际生成 ZIP 和 appcast，并独立用 CryptoKit 验证 ZIP 的 Ed25519 签名，使用 Sparkle 验证清单签名；DMG 只读挂载及包内签名验证通过。
- 原生合成更新应用通过回环 HTTP 实际读取已签名清单：无新版提示正确，篡改清单被拒绝；下载新版、忙碌时延后、用户恢复安装、替换与重启后实际读到 build 22。此合成应用使用同一更新控制器和框架；不等于在完整会议应用上执行了跨版本真实录音更新。
- 最终完整 App 的独立副本使用独立标识、资料目录和端口验证原生更新菜单、设置页、深浅色和滚动可达性。没有打开日常会议、重置 TCC 或替换日常安装。
- 最终 ZIP 的主程序 SHA-256 与已审计 App 完全相同，记录于 `final-source-binding.json`；最终完整 App 的更新开关在正常退出重开后仍保持。GitHub 尚未发布清单时实际显示获取更新信息失败，未误报为最新版本。
- 独立只读复核发现并修复延后安装失败后的旧闭包问题；Sparkle 上游源码确认正常退出、等待宿主退出后替换的链路。现有笔记保存失败检查与该链路分别有证据，未将它们冒充一次完整应用的故障更新实测。

本次不发布 GitHub、不做 Apple 公证、不宣称跨设备、真实硬件录音或公网完整升级已验证。远端启用仍需上述正式 Release 发布及下载后的验证。
